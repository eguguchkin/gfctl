### 1. install-probe — РЕАЛИЗОВАН (§3 не правил по существу, добавил нюанс)

**Решение**: SPEC §3 обещает probe на install («probe-подбор контекста (для
мульти-профилей)») — реализация дешевле и честнее, чем правка §3, т.к.
`probe_context` (2.1) переиспользуется 1:1. Синтаксис: между весами и юнитами
(порядок SPEC-строки «веса → probe → юниты → старт»), для мульти-профилей
(лестница ≠ `-`) и только когда (а) сервер ещё НЕ healthy (healthy-путь
идемпотентности = 0 podman run не трогаем) и (б) канона пары нет (повторный
install не пере-перебирает найденное — «Идемпотентен» §3). Отказ всей
лестницы = die probe_context («это тоже результат», как в use). Канон
записывается `write_canon(prof, sessions, ctx)`, где ctx = probe-факт >
канон пары > поле 4 таблицы — побочно чинит скрытую регрессию канона:
прежний install всегда писал поле 4, затирая активный контекст найденного
probe'ом. После успешного probe — `wait_health` без второго recreate
(контейнер уже поднят попыткой, как в use).

- где: `lib/commands.sh:493–517` (probe-блок cmd_install),
  `lib/commands.sh:518–531` (три пути старта: healthy / probe_path /
  recreate), докстринг cmd_install `lib/commands.sh:448–465`;
- спека: `.dev/SPEC.md` §3 строка install — добавлена скобка
  «при уже зафиксированном каноне пары или на healthy-повторе —
  пропускается: идемпотентность» (семантика уточнена, не изменена);
- usage-шапка диспетчера (`gfctl:10–14`) — install описывает probe-шаг;
- ассерты: батарея §43 (5 шт: probe объявлен+SMOKE, канон пары в .env,
  лестница 196608 fail → 163840 ok ровно 2 run, журнал попыток,
  повтор install с каноном = «probe пропущен» + ровно 1 recreate;
  single — без probe, журнал не создаётся).

## Known limitations / assumptions

- json_str экранирует только `"` `\` `\t` `\n` `\r`; прочие управляющие
  символы (< 0x20) не встречаются в именах моделей/путях инсталляции
  (живой источник спецсимволов — имена gufo, F20) — закомментировано в
  контракте функции.
- part>pin: .part БОЛЬШЕ пин-размера не обработан специально (curl `-C -`
  с него стартует → SHA-MISMATCH → удаление → самовосстановление следующим
  запуском; отдельное сообщение про «удали .part руками» — review 1.1 №5
  остаётся в backlog, не входит в 8 пунктов brief).
- install-probe на healthy-пути с отсутствующим каноном пары НЕ запускает
  probe (сервер не трогаем) — ctx тогда берётся из поля 4 таблицы; на
  следующем реальном `use` probe отработает штатно.
- Граница RED: BF16(30)/MXFP4(39)/TQ(34,35) на ffn считаются КРАСНЫМИ по
  {t>29} без отдельной живой валидации таких тензоров (в наблюдённых
  сетах их на ffn не было; консервативно — «неизвестная экзотика в FFN →
  не грузится»).
